# Writing Style (Human-Facing Output)

인간이 읽는 산출물 — PR 본문, 커밋 메시지, 이슈·리뷰 코멘트, `docs/`의 사람용 문서,
세션 요약 — 의 **문체** 표준. 구조·형식은 `templates/pr_body.md`와
[`harness-doc_standards.md`](harness-doc_standards.md)가, 언어 선택(한/영 분리)은
[`harness-documentation_policy.md`](harness-documentation_policy.md)가 담당하고, 본 문서는
"문장을 어떻게 쓸지"만 다룬다. 어조의 바탕은 글로벌 규칙의 경어체(해요체/합니다체)
일관 원칙이며, 본 문서는 그 위에 가독성 기준을 얹는다.

집행 주체: `owner: local-policy` — 자동 게이트 없음. 리뷰(self-check 포함)에서 적용한다.

## Rules

### R1. 두괄식 — 결론 먼저

- 첫 1–2문장에 "무엇을, 왜"를 담는다. PR이면 첫 단락만 읽고도 리뷰어가
  변경 의도와 병합 판단 기준을 알 수 있어야 한다.
- 배경 설명, 탐색 과정, 시행착오는 결론 **뒤에** 배치한다.

### R2. 문장 우선, 불릿은 병렬 나열에만

- 인과·서사·판단이 담긴 내용은 산문(문장)으로 쓴다.
- 불릿은 대등한 항목의 병렬 나열에만 사용하고, 중첩은 2단계까지만.
- "불릿 폭탄" 금지: 문서 전체가 불릿의 나열이면 산문으로 다시 쓴다.

### R3. 자연스러운 한국어 — 번역투·기계투 금지

- 금지 패턴 예: "~를 수행하였습니다" → "~했습니다", "~에 대한 지원을 추가했습니다"
  → "~를 지원합니다", 과도한 명사화("검증의 수행") · 불필요한 수동태("~가 추가되었습니다"
  → "~를 추가했습니다").
- 판단 기준: 소리 내어 읽었을 때 동료가 쓴 말처럼 들려야 한다.

### R4. 근거 없는 수식어 금지

- "완벽하게", "대폭", "혁신적으로", "깔끔하게" 같은 평가어는 수치·관찰 가능한
  사실로 대체한다. 예: "성능 대폭 개선" → "p95 120ms → 45ms".
- 자기 작업에 대한 자화자찬 문구를 넣지 않는다. 평가는 리뷰어의 몫이다.

### R5. 독자 기준 정보 선별

- PR 본문: 리뷰어가 diff를 열기 **전** 알아야 할 것(의도, 설계 판단, 위험, 검증
  방법)을 담는다. diff에서 자명한 파일별 변경 나열은 반복하지 않는다.
- 문서: 독자가 읽고 나서 할 다음 행동을 기준으로 내용을 고른다. 에이전트 내부
  절차(도구 호출 순서, 중간 산출물 경로)는 독자에게 필요할 때만 남긴다.

### R6. 장식 최소화

- 이모지 금지 — markdown 문서는 [`harness-documentation_policy.md`](harness-documentation_policy.md)의
  MUST와 동일하게 예외 없이 금지한다.
- 굵은 글씨 강조는 문단당 1회 이내. 표는 비교 축이 2개 이상일 때만 사용한다
  (단순 목록을 표로 만들지 않는다).

### R7. 기술 용어 표기 — 과잉 번역도, 통째 음차도 금지

한국어 산문 안의 기술 용어는 아래 순서로 표기를 정한다:

1. **저장소에 실제로 정의된 고유 식별자**(게이트·러너·클래스·도구·설정 키의
   정확한 이름)는 원문을 코드체로 보존하고, 첫 등장에 역할을 한국어로 덧붙인다:
   "`archive-guard` 게이트(로컬 아카이브 커밋 차단)". gate·runner 같은 보통명사
   조합을 곧바로 고유 명칭으로 간주하지 말고, 저장소에 정의된 정확한 이름인지
   먼저 확인한다.
2. **일반 개념어**는 확립된 한국어 역어가 있을 때만 번역한다(멱등성, 동시성,
   직렬화 등). 역어가 없거나 어색하면 영문을 유지한다 — 억지 조어 금지:
   "영속 멱등성"처럼 의미가 불분명한 직역어는 원 개념(durable인지 persistent인지
   등)을 확인한 뒤, 원어를 쓰고 첫 등장에 문맥상 의미를 덧붙인다.
3. 고유 식별자가 아닌 **일반 표현**은 소리만 옮기지 않는다. 실제 정의된 이름이면
   1번을 따르고, 아니면 기능 중심 한국어로 풀어쓴다: "오프라인 게이트" →
   "네트워크 없이 실행되는 검증 단계". 단독으로 관용이 굳은 음차(로그, 파서,
   마이그레이션 등)는 허용.
4. **일관성**: 같은 문서 안에서 같은 용어는 한 표기로 통일한다. 첫 등장 시
   "idempotency(멱등성)"처럼 1회 병기는 허용.

판단 기준 두 가지: 독자가 그 표기로 코드·문서를 **검색할 수 있는가**, 그리고
문맥 또는 첫 등장의 병기·설명으로 의미를 이해할 수 있는가. 통째 음차·억지
번역은 둘 다 끊는다. 용어를 넘어 개념 설명 자체도 영어로 쓰는 편이 훨씬
이해하기 쉬우면 문장·구 단위로 영어를 그대로 써도 무방하다.

## Self-check

제출 전에 한 번 묻는다: **"이 글을 받은 동료가 '기계가 썼구나'라고 느낄까?"**
— 그렇다면 다시 쓴다. 전형적 신호: 전부 불릿, 결론 없는 나열, 근거 없는 수식어,
번역투 종결어미, 통째 음차·억지 번역 용어.
